# FitSync ML service

Generates workout plans from the live exercise catalogue. Node calls this
service; it never calls Node.

## What it does and does not do

- It reads four reference tables — `exercises`, `equipment`,
  `exercise_equipment_requirements`, `exercise_contraindications` — with a
  read-only account. It never reads a user row: every user field arrives in the
  request body.
- Plans are generated by rules. There is no trained model, and `/health`
  reports `"model": "absent"` to say so. When one exists it may only re-rank or
  narrow what the rules produced, never add to it.
- `/injury-risk` has no caller yet. Until the morning check-in route exists it
  returns the same conservative floor the Node stub returns.

## Install

```bash
cd ml
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env   # then fill in FITSYNC_DB_PASSWORD
```

Create the read-only database account first — the grant is in
`server/MIGRATIONS.md`. The service refuses to start without credentials.

## Run

```bash
.venv/bin/uvicorn app.main:build --factory --port 8000
```

Check it:

```bash
curl localhost:8000/health
# {"status":"ok","model":"absent","mode":"rules"}
```

## Test

```bash
DB_NAME=fitsync_test npm run migrate      # from server/, once
cd ml && .venv/bin/python -m pytest tests/ -v
```

The integration tests create and remove their own fixture rows; they do not
need the catalogue seed. If they skip, the test database has not been migrated.

## Point Node at it

In `server/.env`:

```
ML_MODE=http
ML_SERVICE_URL=http://localhost:8000
```

Restart the Node server. `ML_MODE=stub` is the default and remains valid — the
two are interchangeable by design, and every assertion in
`server/tests/ml-service.test.js` holds against both.
